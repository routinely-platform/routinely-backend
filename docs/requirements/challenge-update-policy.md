# 챌린지 수정 정책

## 범위

`challenge-service`가 MVP에서 구현하는 챌린지 수정 규칙을 정리한다.

## 공개 여부 (`isPublic`)

**MVP에서는 `isPublic: false` 요청을 요청 계층(`UpdateChallengeRequest`)에서 `400`으로 거부한다 (#160).**
비공개 챌린지는 들어올 경로가 없어 만들 수 없게 막았는데, `PATCH`를 열어 두면 "공개로 만든 뒤 비공개로
전환"으로 그냥 우회된다. 아래 표의 공개 → 비공개 규칙은 **v2에서 비공개를 열었을 때** 살아난다.

| 상태 | 활성 멤버 수 | 비공개 → 공개 | 공개 → 비공개 |
|---|---:|:---:|:---:|
| `WAITING` / `ACTIVE` | 1명 | 허용 | **MVP 거부** (v2: 허용) |
| `WAITING` / `ACTIVE` | 2명 이상 | 허용 | 거부 |
| `ENDED` | 무관 | 거부 | 거부 |

규칙:

- 비공개 → 공개 전환은 MVP에서도 허용한다. 이미 만들어진 비공개 챌린지를 여는 방향이기 때문이다.
- 비공개 → 공개 전환 시 기존 `inviteCode`를 유지한다 (재비공개 전환 대비).
- 공개 → 비공개 전환 시 `inviteCode`가 없는 경우에만 새로 생성한다.
- 다른 멤버가 참여한 상태에서 공개 → 비공개 전환은 거부한다. 참여·공유 방식이 달라지기 때문이다.
- 종료(`ENDED`)된 챌린지는 방향에 관계없이 공개 여부 변경이 불가능하다.

## 기타 필드

대상 필드: `title`, `description`, `maxMembers`, `startedAt`, `endedAt`

| 상태 | 활성 멤버 수 | 수정 가능 항목 |
|---|---:|---|
| `WAITING` | 1명 | 위 필드 전체 |
| `WAITING` | 2명 이상 | `description`, `maxMembers` 증가만 허용 |
| `ACTIVE` / `ENDED` | 무관 | 없음 |

추가 규칙:

- `startedAt`은 오늘 이후 날짜여야 한다.
- 부분 수정 후 최종 날짜 범위는 `startedAt <= endedAt` 을 만족해야 한다.
- 부분 수정 후 **최종 기간은 시작일·종료일을 모두 포함해 100일 이하**여야 한다
  (`ChallengePolicy.MAX_PERIOD_DAYS`, #160). 한쪽 날짜만 오면 나머지는 저장된 값을 쓰므로,
  이 판정만은 요청 DTO가 아니라 서비스 계층에서 병합 후 수행한다.
- `maxMembers`는 20 이하여야 한다 (`ChallengePolicy.MAX_MEMBERS`, #160).
- `categoryCode`, `creatorUserId`, 루틴 반복 설정, 루틴 소유자 관련 필드, 챌린지 연결 필드는 이 API로 변경할 수 없다.
- 루틴 제목·선호 시간 수정은 routine-service gRPC 연동 전까지 의도적으로 거부한다.

## 검증 순서

1. 챌린지를 조회하고, 요청자가 활성 상태의 `LEADER`인지 확인한다.
2. 루틴 필드 수정 요청이 있으면 routine-service 연동 전까지 거부한다.
3. 활성 멤버 수를 조회한다. 0이면 데이터 정합성 오류로 처리한다 (LEADER가 이미 확인됐으므로 1 이상이어야 한다).
4. 공개 여부 변경을 상태·멤버 수·방향 기준으로 검증한다.
   (MVP의 `isPublic: false` 차단은 그 앞 요청 계층에서 이미 끝난다.)
5. 기타 필드 변경을 상태·멤버 수 기준으로 검증한다.
6. 모든 검증을 통과한 후에만 값을 실제로 반영한다.
