# ADR-0038: 루틴 실행 기록 저장 전략 — sparse(완료만 저장, 미완료 파생)

- **Status**: Accepted
- **Date**: 2026-07-24 (2026-08-22 개정 — 저장 원칙 재정의, 백필 허용, 중단 루틴 파생 규칙 / 2026-08-23 개정 — 챌린지 백필 창 3일 확정, 사진·메모를 feed_cards로 이동, 취소 이벤트 신설)
- **Author**: Routinely Project

---

## 1. Context

루틴 일별 실행 기록(`routine_executions`)을 언제/어떻게 생성할지 결정해야 한다. 초기 초안(사전 생성
전략)은 루틴 시작 시 전 기간을 PENDING으로 미리 INSERT하고 완료를 상태 전이(PENDING→COMPLETED)로
처리하는 방식이었다. 그러나 #149(ADR-0039)에서 반복 스케줄 모델을 이원화하면서 **"오늘 이 루틴이
대상인가"(due 판정)가 스케줄 유형으로 결정 가능**해졌고, 사전 생성의 전제가 흔들렸다.

사전 생성 방식의 문제:
- **빈도형(WEEKLY_COUNT/MONTHLY_COUNT)** 은 "아무 날이나 N회"라 특정일 PENDING을 미리 박을 근거가 없다.
  미수행일을 MISSED로 세면 달성률이 왜곡된다(월 3회를 3회 다 해도 3/30).
- 루틴 시작마다 전 기간(수십~수백 행)을 INSERT → 쓰기 비용·저장 공간 낭비. 대부분 PENDING인 채로 남는다.
- 루틴 중단·기간 변경 시 미래 PENDING을 삭제/재생성하는 정리 로직이 필요하다.
- 미완료 확정(MISSED)을 위한 일 마감 스케줄러가 필요하다.

핵심 질문: 실행 기록을 **미리 채울 것인가(dense)**, **완료 시에만 채울 것인가(sparse)**?

---

## 2. Decision

**sparse 저장 — 사용자가 명시적으로 남긴 행동만 저장하고, 시스템이 판단하는 상태는 저장하지 않고 조회 시 파생한다.**

저장 여부를 가르는 기준은 "완료인가"가 아니라 **"사용자가 남긴 것인가, 시스템이 계산한 것인가"** 다.

| | 예 | 저장 |
|---|---|---|
| 사용자가 명시적으로 남긴 행동 | `COMPLETED` (향후 `SKIPPED` 등) | **저장한다** |
| 시스템이 스케줄로 판단하는 상태 | `PENDING`, `MISSED` | **저장하지 않고 파생한다** |

현재 사용자가 남기는 행동은 완료뿐이라 저장되는 값도 `COMPLETED` 하나다. 이 기준을 세워 두는 이유는,
"오늘은 쉬어감"(`SKIPPED`)처럼 **사용자가 선언하는 상태**가 추가될 때 원칙을 바꾸지 않고 확장하기 위해서다.
그때는 `ck_re_status` CHECK를 함께 넓힌다. 반대로 시스템이 계산하는 값은 앞으로도 저장하지 않는다.

- 루틴 시작 시 실행 기록을 만들지 않는다(행 0개).
- 완료 처리 = `(routine_id, scheduled_date)` 기준 `COMPLETED` 행 **신규 생성**(UNIQUE로 멱등).
- 완료 취소 = 해당 행 **삭제**(상태 전이 아님).
- 조회 = 저장된 행 + **스케줄 due 판정으로 파생한 PENDING/MISSED** 를 병합.

### 파생 규칙 (ADR-0039 스케줄 유형 기반)

| 유형 | 오늘 | 과거(미완료) | 미래(미완료) |
|---|---|---|---|
| `DAILY` | PENDING | MISSED | PENDING |
| `SPECIFIC_DAYS` | 지정 요일이면 PENDING | 지정 요일이면 MISSED | 지정 요일이면 PENDING |
| `WEEKLY_COUNT`/`MONTHLY_COUNT` | PENDING(수행 가능) | 표시 안 함(결석 아님) | 표시 안 함(진행률로만) |

- **수행 가능(completable)**: 지정형은 지정 요일만, 빈도형·DAILY은 아무 날 → 완료 API 검증 기준.
- **의무(obligation)**: 지정형·DAILY만 의무 → 미완료 시 MISSED/예정. 빈도형은 per-day 의무 없음.
- 빈도형은 이번 주/달 목표를 이미 채웠어도 오늘 PENDING으로 계속 표시한다. 목록에서 사라지게 하지 않고,
  진행률(#60)로 "3/3 달성"을 함께 보여준다. 추가 수행을 막을 이유가 없고, 목록에서 없애면 오히려 위축된다.

### 백필 — 지난 날짜의 완료를 허용한다

완료·완료 취소는 **아직 오지 않은 날만 아니면 수행 기간 내 어느 날짜든 허용한다.**

깜빡하고 인증을 못 누른 하루 때문에 MISSED가 영구히 남으면, 이 서비스의 목적("꾸준함을 북돋는다")과
정면으로 어긋난다. sparse에서 MISSED는 저장된 사실이 아니라 **완료 기록이 없어서 계산된 값**이므로,
지난 날짜를 채우면 그 자리의 MISSED는 자동으로 사라진다. 되돌릴 데이터가 없다는 점이 이 정책을 싸게 만든다.

| 대상 | 허용 |
|---|---|
| 지난 날짜 완료 | ✅ 수행 기간 내 + 수행 가능 요일이면 허용 |
| 오늘 완료 | ✅ |
| 미래 날짜 완료 | ❌ 아직 오지 않은 날은 완료할 수 없다 |
| 완료 취소 | ✅ 날짜 제한 없음 (잘못 남긴 인증을 지우는 동작) |

#### 챌린지 루틴은 3일 이내만 허용한다 (2026-08-23 확정)

개인 루틴은 수행 기간 내 무제한이고, **챌린지 루틴만 최근 3일로 제한한다.**

기준은 **백필이 무엇을 위한 장치인가**다.

> **백필은 "수행했으나 기록을 놓친 것"을 위한 장치다. "안 한 것"을 위한 게 아니다.**

일주일 출장으로 못 한 것은 실제로 안 한 것이므로 채워주면 안 된다. 반면 밤에 깜빡하고 잔 하루는
채워줘야 하고, **실제로 한 것을 기억해 채우는 데는 3일이면 충분하다.**

어뷰징 관점에서 ADR-0027의 캡이 이미 1차 방어다 — 주 N회 루틴은 지난 주를 지금 채워도 그 주 인정치가
N을 넘지 못한다. **캡이 걸리지 않는 것은 `DAILY` 챌린지뿐**이고 거기가 진짜 위험 지점이다.

| 창 | 30일 `DAILY` 챌린지에서 마지막에 몰아칠 수 있는 양 |
|---|---|
| **3일** | **10%** |
| 5일 | 17% |
| 7일 | 23% |

**숫자보다 UX 보완이 중요하다.** 마감 알림(21:00)이 깜빡할 확률 자체를 줄이고, 화면에 남은 창을
표시한다("8/20 미완료 · 채울 수 있는 날 2일 남음"). 개인 루틴을 무제한으로 두는 이유는 랭킹이 없어
자기기만이 본인 몫이기 때문이다.

**챌린지 종료 후에는 창과 무관하게 채울 수 없다.** 루틴 기간이 챌린지 기간과 같아 종료 다음 날부터
"수행 기간이 아닙니다"로 거부된다. 이 규칙이 3일 창보다 우선하므로 최종 순위가 종료 후에 흔들리지 않는다.

`MISSED`라는 이름은 그대로 둔다. 백필로 언제든 완료할 수 있으면 "놓침"이 확정이 아니라 되돌릴 수 있는
상태가 되므로, 용어를 바꾸지 않아도 사용자에게 막다른 느낌을 주지 않는다.

### 중단(비활성) 루틴 — 파생하지 않는다

`is_active = false`인 루틴은 **완료 이력만 보여주고 PENDING/MISSED를 파생하지 않는다.** 완료 API도 거부한다
(취소는 허용 — 이미 남긴 기록을 지우는 동작이다).

중단은 **개인 루틴에만 가능하다.** 챌린지 루틴은 `DELETE /api/v1/routines/{routineId}`에서 거부한다 —
인스턴스가 멤버 수만큼 존재해 한 사람이 내려도 챌린지가 끝나지 않고(ADR-0036), 중단을 허용하면 파생·집계
제외 규칙을 타고 **랭킹에서 조용히 이탈하는 통로**가 되기 때문이다. 챌린지에서 빠지는 수단은 탈퇴 하나로 둔다.

과거 구간만 파생을 남기는 안도 검토했으나 채택하지 않았다. `routines`에 **중단 시각을 기록하지 않아서**
"중단 이전의 과거"와 "중단 이후의 과거"를 구분할 수 없고, 그대로 두면 **그만둔 뒤의 날짜에까지 MISSED가
붙는다.** 그만둔 루틴의 결석을 보여줄 실익도 없다. 나중에 중단 시각이 필요해지면 `deactivated_at`을 추가해
과거 구간 파생을 되살릴 수 있다.

## 3. Rationale

- **빈도형과 지정형을 모순 없이 담는다.** 빈도형은 per-day MISSED가 없어야 한다는 요구가 "저장 안 함 +
  파생"으로 자연스럽게 성립한다. 달성률 분모는 실제 스케줄 due 수로 계산된다(#60에서 사용).
- **쓰기·저장 절감.** 실제로 저장되는 행 = 사용자가 완료한 날뿐. 대부분이 PENDING인 dense 저장을 피한다.
- **정리 로직 제거.** 루틴 중단/기간 변경 시 삭제할 미래 PENDING이 없다. MISSED 마감 스케줄러도 불필요
  (조회 시 과거 의무일이 곧 MISSED로 파생).
- **due 판정의 단일 출처.** "오늘의 루틴"·통계·피드가 모두 스케줄 + COMPLETED 병합이라는 한 규칙에서 나온다.

트레이드오프: 조회가 단순 SELECT가 아니라 **파생 계산**을 포함한다(스케줄 전개 + 완료 병합). 조회 기간을
경계로 제한(최대 366일)하고, 완료 기록은 `idx_re_user_date`로 조회한다.

## 4. API 계약 (A안 — routineId + date)

행이 사전에 없으므로 `executionId` 기준 완료는 불가능하다. 완료 대상을 `routineId + date`로 지정한다.

```
POST   /api/v1/routines/{routineId}/executions/{date}/complete   # 완료(미래 제외) — multipart: photo·memo(선택)
DELETE /api/v1/routines/{routineId}/executions/{date}/complete   # 완료 취소(날짜 제한 없음)
GET    /api/v1/routine-executions?date= | startDate=&endDate= [&routineId=&status=]   # 파생 병합 조회
```

- 완료: 소유자·**미래 아님**·**활성 루틴**·수행 기간 내·수행 가능 요일 검증, 이미 완료면 409(`EXECUTION_ALREADY_COMPLETED`).
- 사진: MIME(jpeg/png/webp)·5MB·매직넘버 검증 → `FileStorage.upload()`, 롤백 시 오브젝트 보상 삭제.
- 취소: 행 삭제, 사진 오브젝트는 커밋 후 삭제. 날짜·활성 제한 없음.

## 4-1. 사진·메모는 `feed_cards`가 소유한다 (2026-08-23 변경)

초안은 `routine_executions`에 `photo_url`·`photo_object_key`·`memo`를 두었으나, **`feed_cards`에만
두는 것으로 바꾼다.** `routine_executions`에서 세 컬럼을 제거한다(V5 마이그레이션 철회).

개념이 갈린다 — **실행 기록은 "했다는 사실", 피드 카드는 "그것에 대한 게시물"** 이고 사진·메모는
게시물의 속성이다. 한 곳에만 두면 수정·삭제 대상도 하나로 정해진다.

| | 소유 |
|---|---|
| 완료했다는 사실 (`scheduled_date`, `completed_at`) | `routine_executions` |
| 사진 · 메모 | **`feed_cards`** |

**따라오는 것**
- 완료 API는 multipart로 사진·메모를 받아 **`feed_cards`에 INSERT**한다. 테이블은 `V1__init.sql`에
  이미 있으므로 #59(피드 조회·리액션)를 기다리지 않는다.
- 완료 후 사진·메모 수정은 `PATCH /api/v1/feed/{feedCardId}`로 가능하다. **실행 기록을 건드리지 않으므로
  완료 사실·스트릭·달성률이 흔들리지 않는다.** 이 경로가 없으면 취소·재완료라는 우회로밖에 없고,
  그러면 피드 카드가 새로 생겨 받은 리액션이 날아간다.
- 사진 오브젝트의 보상 삭제·커밋 후 삭제는 `feed_cards.photo_object_key` 기준으로 수행한다.

## 4-2. 완료 취소는 피드를 삭제하고 랭킹을 재계산한다 (2026-08-23 확정)

삭제 순서는 FK 역순으로 한 트랜잭션에서 처리한다.

```
feed_reactions  →  feed_cards  →  routine_executions
```

리액션이 달려 있어도 취소를 막지 않는다. 잘못 남긴 인증을 못 지우는 쪽이 더 나쁘다.

### 랭킹은 감소가 아니라 재계산이다

**`completed_count -= 1`은 틀린다.** ADR-0027의 주별·월별 캡 때문이다.

```
주 3회 챌린지에서 이번 주 5번 완료  →  인정 min(5, 3) = 3
하나 취소해서 4번               →  인정 min(4, 3) = 3   ← 줄지 않는다
```

단순 감소로 처리하면 인정치가 3에서 2로 잘못 떨어진다. **해당 주(또는 달)를 다시 집계해야 한다.**

### `routine.execution.cancelled` 토픽 신설

완료 이벤트만 있고 취소 이벤트가 없어 **랭킹이 오르는 경로만 있고 내려가는 경로가 없었다.**

| | |
|---|---|
| Publisher | RoutineService |
| Subscriber | ChallengeService |
| Partition Key | `userId` (`routine.execution.completed`와 동일) |
| 페이로드 | `completed`와 동일 — `userId`·`routineId`·`execDate`·`challengeId` |

소비 측은 **발행 시각이 아니라 `execDate` 기준**으로 해당 기간을 재집계하고 Redis ZSET을 갱신한다
(백필 허용의 파급과 같은 원칙).

## 5. Consequences

### 긍정적
- 빈도형/지정형을 모순 없이 지원, 달성률 왜곡 없음.
- 쓰기·저장 절감, 중단 정리·MISSED 스케줄러 등 부수 로직 제거.
- due 판정 단일 규칙으로 "오늘의 루틴"·통계·피드 일관.

### 부정적
- 조회에 파생 계산 포함 → 서비스 로직 복잡도 증가(스케줄 전개 + 병합). 조회 기간 상한으로 완화.
- 완료 API가 `executionId`가 아니라 `routineId + date` 기반 → 초기 이슈 문서/초안과 계약이 달라짐.

### 후속 이슈에 넘기는 제약 (백필 허용의 파급)

지난 날짜 완료를 허용하면 "완료 처리 시각"과 "수행 날짜"가 갈라진다. 후속 구현은 **수행 날짜(`execDate`)를
기준으로** 동작해야 한다.

| 이슈 | 반영할 것 |
|---|---|
| #61 Outbox | 소비 측이 발행 시각이 아니라 payload의 `execDate`로 처리해야 한다. 페이로드에 이미 필드가 있어 스키마 변경은 없다. |
| #60 통계 | 과거 날짜가 들어오면 **그 날짜의 요약을 갱신**하고 **끊겼던 스트릭을 다시 이어야** 한다. 단순 증가 UPSERT로는 부족하다. |
| #59 피드 | `created_at` 정렬이면 3일 전 인증이 최상단에 뜬다. `scheduled_date` 정렬로 가거나 "3일 전 루틴을 인증했어요" 표기가 필요하다. |
| #58 챌린지 | ~~N일 이내 정책 검토~~ → **2026-08-23 확정: 챌린지 루틴 3일 이내** (위 "챌린지 루틴은 3일 이내만 허용한다" 참고) |

### 향후
- 빈도형 "이번 주/달 N/M" 진행률 집계, 지정형 스트릭·휴가(결석 예외)는 후속(#60 등)에서 파생 규칙 위에 얹는다.
- 사용자가 선언하는 `SKIPPED`(오늘은 쉬어감)를 저장 대상에 추가하는 것을 검토한다. 쉬겠다고 선언한 날은
  MISSED로 세지 않고 스트릭도 끊지 않는다 — 본 ADR의 저장 원칙을 그대로 따르는 확장이다.
