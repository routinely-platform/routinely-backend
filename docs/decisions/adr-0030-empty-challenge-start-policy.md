# ADR-0030: 시작일 도래 시 멤버 미달 챌린지의 처리 정책

## Status
Accepted

---

## Context

스케줄러가 챌린지 상태를 `WAITING → ACTIVE`로 전이하는 시점에, 참여자가 방장 1명뿐인 챌린지를 어떻게 처리할지 결정이 필요했다.

검토한 옵션:

1. **시스템 자동 폐기** — 멤버 수가 임계치 미만이면 `CANCELLED` 상태로 전환
2. **정상 시작** — 멤버 수와 무관하게 `ACTIVE`로 전이

---

## Decision

**멤버 수와 무관하게 모든 챌린지를 정상 시작(`ACTIVE`)으로 전이한다.**

---

## Rationale

### 1. 챌린지의 본질은 루틴 실천이다

Routinely에서 챌린지는 공동 약속의 형태를 띠지만, **개인의 루틴 실천이 핵심 가치**다. 리더보드와 멤버 간 비교는 동기부여를 위한 부수 기능이지 챌린지 존재의 조건이 아니다. 따라서 멤버 수가 챌린지 운영의 가부를 결정해서는 안 된다.

### 2. 방장의 의지를 존중한다

방장이 챌린지를 만든 행위 자체가 "이 루틴을 하겠다"는 약속이다. 시작일까지 챌린지를 유지한 것도 본인의 의지 표현이다. 시스템이 멤버 미달을 이유로 일방 폐기하는 것은 사용자 의지 침해이며 신뢰를 손상시킨다.

### 3. 데이터 무결성과 단순성

자동 폐기를 도입하면 다음 처리가 필요하다.
- 신규 상태(`CANCELLED`) 정의 및 상태 전이 다이어그램 확장
- 멤버 정리, 알림 발송, 챌린지 노출 처리 등 추가 로직
- "왜 갑자기 챌린지가 폐기됐는지" 사용자 문의 대응

도메인을 단순하게 유지하는 편이 운영·디버깅·확장에 유리하다.

### 4. 진행 중 합류 가능성 (v2)

> **2026-08-23 정정** — 본 절은 원래 "채택된 `allow_mid_join` 정책에 따라 진행 중인 챌린지에도 새 멤버가
> 합류할 수 있다"고 적었으나 **사실과 다르다.** `allow_mid_join`은 채택된 적이 없고, MVP는 정반대로
> **`WAITING` 상태에서만 참여할 수 있다**(`ChallengeService.joinChallenge()`가 `CHALLENGE_ALREADY_ACTIVE`로
> 거부). 진행 중 참여는 #118의 `joinableUntilPercent`로 **v2에 이관**됐다.

v2에서 `joinableUntilPercent`가 도입되면 방장 혼자 시작한 챌린지도 며칠 후 다른 사용자 합류로 활성화될
가능성이 생긴다. 시작 자체를 막으면 그 가능성까지 차단된다. **단 이는 v2 전제이므로 본 결정의 주된
근거는 1~3번**이며, 4번은 부수적 이점으로만 읽는다.

### 5. 유사 서비스 사례

디스코드 서버, 카카오톡 오픈채팅, Strava 챌린지 등 유사 도메인 서비스 모두 멤버 미달을 이유로 시스템 자동 폐기를 하지 않는다. **사용자 의지 존중**이 업계 표준이다.

---

## Consequences

### Positive

- 도메인 단순성 유지 (`CANCELLED` 상태 불필요)
- 사용자 신뢰 보호
- 방장 혼자 시작 → `allow_mid_join`을 통한 신규 합류 경로 유지
- 방장의 루틴 실천 의지 보존
- 본인 통계(`routine_daily_summary`)에 챌린지 활동이 정상 반영

### Negative

- 멤버 1명뿐인 챌린지가 데이터셋에 존재 → 분석 시 노이즈 가능성
- 공개 챌린지 목록의 "인기순" 정렬에서 자연스럽게 후순위로 밀리므로 노출 측면 영향은 미미

### Neutral

- 시작 전날(D-1) 방장에게 "현재 참여자 1명, 내일 시작 예정" 알림 발송 → 방장의 자율 판단 기회 제공 (시작일 변경, 챌린지 정보 수정 등)

---

## Implementation Notes

- 챌린지 상태 전이 스케줄러는 멤버 수 검증 없이 `started_at <= today AND status = 'WAITING'` 조건만으로 전이 수행
- D-1 알림은 별도 스케줄러 또는 동일 스케줄러 내 분기 처리로 구현 가능
- `routine_executions` 사전 생성(DAILY 타입)도 멤버 수 무관하게 정상 수행

---

## Future Considerations

향후 운영 중 다음과 같은 상황이 관측되면 본 정책의 재검토가 필요할 수 있다.

- 멤버 1명 챌린지가 전체 챌린지의 상당 비율을 차지해 데이터 노이즈가 분석을 방해할 때
- 운영팀에서 자동 정리 요청이 발생할 때
- 방장이 챌린지를 만들고 방치하는 어뷰징 패턴이 발견될 때

이 경우 `CANCELLED` 상태 추가 또는 일정 기간 후 자동 종료 정책을 도입한다. 현 시점에는 `status` enum 확장 여지를 유지하는 수준으로 충분하다.
