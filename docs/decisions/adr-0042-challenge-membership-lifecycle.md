# ADR-0042: 챌린지 멤버십 생애주기 — 리더 승계, 빈 챌린지 삭제, 탈퇴 멤버 기록

- **Status**: Accepted
- **Date**: 2026-08-23
- **Author**: Routinely Project

---

## 1. Context

`ChallengeService.leaveChallenge()`는 이미 방장 탈퇴를 두 갈래로 처리하고 있다 — 다른 활성 멤버가 있으면
가장 먼저 참여한 멤버에게 자동 승계하고, 없으면 챌린지를 `ENDED`로 종료한다. 그런데 **이 규칙이
api-spec에도 ADR에도 없다.** 근거는 `portfolio/interview-qa.md`에만 남아 있어, 규약을 찾으러 오는
사람이 닿지 못한다.

정해지지 않은 것도 셋 있다.

1. **승계 대상을 방장이 지목할 수 있는가.** 지금은 `joinedAt` 오름차순 자동 승계뿐이다.
2. **승계당한 사람이 그 사실을 어떻게 아는가.** `ChallengeMemberLeftEvent`에 승계 정보가 없어
   새 방장은 자기가 방장이 된 것을 모른다.
3. **시작도 안 한 챌린지에 방장 혼자 있다가 나가면.** 지금은 `ENDED`가 되어, 시작한 적 없는 챌린지가
   "종료됨"으로 남고 내 챌린지 목록에 계속 쌓인다.

그리고 탈퇴·강퇴한 멤버의 기록(실행 기록·피드 카드·채팅·랭킹)을 어떻게 다룰지도 정의된 적이 없다.

## 2. Decision

### 2.1 방장 탈퇴는 상태와 남은 멤버 수로 넷으로 갈린다

| 상태 | 활성 멤버 | 처리 |
|---|:---:|---|
| `WAITING` | **1 (혼자)** | **챌린지를 하드 삭제한다** |
| `WAITING` | 2+ | 승계 |
| `ACTIVE` | 1 (혼자) | `ENDED`로 종료 |
| `ACTIVE` | 2+ | 승계 |

### 2.2 승계 대상 지목은 선택이다

```jsonc
POST /api/v1/challenges/{challengeId}/members/me/leave
{ "newLeaderUserId": 42 }   // 선택. 없으면 joinedAt 오름차순 첫 활성 멤버가 자동 승계
```

지정한 사용자가 그 챌린지의 활성 멤버가 아니면 `400 VALIDATION_FAILED`.
**승계당한 사람이 거부할 수단은 두지 않는다.**

### 2.3 승계 정보를 이벤트에 담는다

```java
ChallengeMemberLeftEvent(eventId, occurredAt, challengeId, userId, reason,
                         Long newLeaderUserId)   // 승계가 없으면 null
```

### 2.4 빈 챌린지 하드 삭제

```
DELETE challenge_member_summary  →  challenge_members  →  challenges   (한 트랜잭션)
+ challenge.deleted 이벤트 발행 (Outbox)
```

`challenge.deleted` 구독자는 RoutineService이며, 해당 챌린지의 루틴 템플릿을 정리한다.
파티션 키는 `challengeId`로 `challenge.created`와 동일하게 둔다.

### 2.5 탈퇴·강퇴 멤버의 기록

**개인의 수행 기록은 지우지 않고, 그룹 화면에서의 노출만 조정한다.**

| 대상 | 처리 |
|---|---|
| 실행 기록 | 유지 |
| **챌린지 루틴 인스턴스** | **`is_active = false`** (하드 삭제 아님) |
| 피드 카드 · 사진 | 유지 — **실명 그대로** |
| 채팅 메시지 | 유지 — **실명 그대로** |
| 랭킹 · 멤버 목록 | **제외** (`status = ACTIVE`만) |
| 탈퇴 기간의 달성률 분모 | **포함** |

강퇴는 예외로 **피드 카드를 숨긴다**(삭제 아님). 강퇴 기능 자체는 MVP 범위 밖이므로 v2에서 확정한다.

### 2.6 `challenge.member.left` 구독자를 셋으로 늘린다

지금 구독자는 ChatService뿐이라 **ADR-0038이 약속한 "챌린지에서 빠지는 수단은 탈퇴 하나"가 실제로는
배선되어 있지 않다.** 탈퇴해도 챌린지 루틴이 활성으로 남아 오늘 할 일에 계속 뜨고, 개인이 내릴 수도 없다.

| 구독자 | 할 일 |
|---|---|
| **RoutineService** (신규) | 챌린지 루틴 인스턴스 `is_active = false` |
| **ChallengeService** (추가) | `challenge_member_summary` 랭킹 제외 + Redis ZSET `ZREM` |
| ChatService (기존) | 채팅방에서 나가기 |

하드 삭제가 아니라 비활성화인 이유는 `routine_executions.routine_id` FK 때문이다. 행을 지우면
**실행 기록도 함께 지워야 해서 지난 인증이 사라진다.** 비활성화하면 중단 규칙(ADR-0038)이 그대로
적용되어 오늘 할 일·달성률에서는 빠지고 **달력의 완료 이력은 남는다.**

## 3. Rationale

### 3.1 지목을 강제하면 탈퇴 흐름이 막힌다

지목을 필수로 하면 곧바로 "지목 대상이 거절하면?"이 나오고, 수락 절차를 붙이면 **방장이 잠수했을 때
아무도 못 나가는 교착**이 생긴다. 선택으로 두면 방장의 의사를 존중하면서도 흐름을 막지 않는다.
검증은 "그 사용자가 활성 멤버인가" 한 줄이다.

같은 이유로 **승계 거부도 두지 않는다.** 방장 권한이 하는 일이 좁고(수정·이미지 관리), 부담스러우면
본인도 탈퇴하면 된다. 거부를 허용하면 "아무도 안 받으면 챌린지는 어떻게 되나"가 다시 열린다.

`joinedAt` 오름차순 자동 승계를 기본값으로 유지하는 이유는 **예측 가능하고 결정적**이기 때문이다.
달성률 1위 승계는 랭킹과 방장직을 얽어 "1등이 되면 방장이 될 수 있다"는 이상한 유인을 만든다.

### 3.2 알림은 못 만들어도 이벤트 필드는 지금 넣는 게 싸다

notification-service가 껍데기라 승계 알림 자체는 지금 만들 수 없다. 그러나 **페이로드는 나중에 바꾸면
소비자 전부가 영향을 받는다.** 현재 `challenge.member.left` 소비자는 ChatService뿐이고 새 필드를 무시하면
그만이므로, 지금 넣는 비용이 사실상 0이다.

이 필드가 없으면 **새 방장은 자기가 방장이 된 것을 영영 모른다** — 챌린지 상세를 다시 열어봐야 안다.

### 3.3 시작도 안 한 챌린지를 `ENDED`로 남기는 것은 거짓 기록이다

`WAITING`은 아직 아무 일도 일어나지 않은 상태다. 멤버 0, 인증 0, 피드 0, 채팅방 0(방은 시작 시 생성),
랭킹 0. **남길 가치가 있는 데이터가 실제로 없다.** 그런데도 `ENDED`로 두면 "시작한 적 없는 챌린지가
종료됨"이라는 사실과 다른 기록이 남고, 내 챌린지 목록에 만들다 만 껍데기가 쌓인다.

**서비스 경계를 넘는 정리는 생각보다 가볍다.** `routine_templates.challenge_id`는 FK가 아니므로
(서비스 경계상 FK 불가) 챌린지 행을 지워도 정합성이 깨지지 않는다. 그 템플릿은 어느 화면에도 나오지
않는다 — 목록은 `challenge_id IS NULL`만 반환하고 상세·수정·삭제는 모두 403이며, 인스턴스도 없다
(`challenge.started`가 오지 않았으므로).

그래도 고아를 방치하지 않기 위해 `challenge.deleted`로 정리한다. **`challenge.created`와 파티션 키가
같아 순서가 보장되므로**, 생성 이벤트가 아직 소비되지 않은 상태에서 삭제 이벤트가 먼저 처리되어
템플릿이 되살아나는 경합은 발생하지 않는다.

`ACTIVE`를 하드 삭제하지 않는 이유는 명확하다 — 시작했으면 멤버별 루틴 인스턴스가 생성됐고 인증 기록이
쌓였을 수 있다. 다른 서비스에 흩어진 데이터를 동기적으로 정리할 수 없다.

> ADR-0030은 `CANCELLED` 상태를 두지 않기로 했다. 본 결정은 그것과 충돌하지 않는다 — ADR-0030의 맥락은
> **시스템이 멤버 미달을 이유로 자동 폐기**하는 것이었고, 여기는 **사용자의 명시적 탈퇴**다. 새 상태를
> 만들지 않고 행을 지우므로 상태 전이 다이어그램도 그대로다.

### 3.4 기록은 지우지 않고 노출만 조정한다

탈퇴는 "내가 이 그룹에서 나간다"이지 "내가 남긴 것을 없앤다"가 아니다.

- **피드 카드·채팅을 지우면 남은 멤버의 기록에 구멍이 난다.** 리액션을 주고받은 게시물이고 대화는 혼자
  만든 것이 아니다.
- **작성자 이름은 실명 그대로 둔다.** 계정 탈퇴와 혼동하기 쉬운 지점이다 — 계정 탈퇴는 "서비스를
  떠난다"라 사진을 지우고 이름을 가려야 하지만, **챌린지 탈퇴는 "이 그룹에서 나간다"일 뿐이고 계정은
  살아 있다.** 어제까지 같이 하던 사람이 갑자기 "탈퇴한 사용자"가 되면 이상하고, 재참여하면 실명으로
  돌아와 왔다 갔다 한다. 피드 카드에 "나간 멤버" 배지 정도만 붙인다.
- **랭킹에서는 빼야 한다.** 없는 사람과 경쟁하는 화면은 이상하다. Redis ZSET에서도 `ZREM`해야 하므로
  `challenge.member.left` 처리에 함께 넣는다.
- **탈퇴 기간을 분모에서 빼지 않는다.** 빼주면 "못 할 것 같은 주에 나갔다가 돌아오기"가 유리해져
  달성률이 조작 가능해진다. 탈퇴는 본인의 선택이었다.

강퇴만 피드를 숨기는 이유는 강퇴 사유가 대개 부적절한 콘텐츠이기 때문이다. 삭제가 아니라 숨김인 것은
오판으로 강퇴했을 때 되돌릴 수 있게 하기 위해서다.

## 4. Consequences

### 긍정적
- 코드에만 있던 승계 규칙이 문서화되어 규약을 찾을 위치가 생긴다.
- 빈 챌린지가 목록에 쌓이지 않고, "종료됨"이라는 거짓 기록도 남지 않는다.
- 새 방장이 승계 사실을 알 수 있는 경로가 열린다(알림 구현 시점에 바로 쓸 수 있다).
- 지목을 선택으로 둬 방장의 의사를 반영하면서도 탈퇴 교착이 생기지 않는다.

### 부정적
- **하드 삭제가 서비스 경계를 넘는 정리를 동반한다.** `challenge.deleted` 소비자가 유실되면 고아 템플릿이
  남는다(정합성은 안 깨지지만 데이터가 지저분해진다).
- 탈퇴 멤버에 "나간 멤버" 배지를 붙이려면 **피드·채팅 조회 시 멤버십 상태를 함께 봐야 한다.**
- 승계 거부 수단이 없어, 원치 않는 사용자가 방장이 되는 경우가 생긴다. 본인이 탈퇴하면 그다음 사람에게
  다시 넘어가므로 교착은 없다.
- 강퇴 관련 규칙(피드 숨김)은 강퇴 기능이 없어 **당장 검증할 수 없다.**

### 구현 영향

| 대상 | 변경 |
|---|---|
| `POST /challenges/{id}/members/me/leave` | `newLeaderUserId` 선택 파라미터 수용 + 활성 멤버 검증 |
| `ChallengeService.leaveChallenge()` | `WAITING` + 혼자면 하드 삭제 분기 추가 |
| `ChallengeMemberLeftEvent` | `newLeaderUserId` 필드 추가 |
| `event-spec.md` | `challenge.member.left` 페이로드 갱신 + **`challenge.deleted` 토픽 신설** |
| routine-service | `challenge.deleted` 소비자 추가 (챌린지 템플릿 정리) |
| challenge-service | `challenge.member.left` 처리에 Redis ZSET `ZREM` 추가 |
| **routine-service** | **`challenge.member.left` 소비자 신설** — 챌린지 루틴 비활성화 (§2.6) |
| api-spec | 탈퇴 API에 승계·삭제 규칙 명시 |

## 5. 관련 결정

- **ADR-0030**: 멤버 미달 챌린지의 정상 시작 — `CANCELLED`를 두지 않기로 한 결정. 본 결정은 상태 추가 없이 행 삭제로 처리해 충돌하지 않는다.
- **ADR-0031**: 초대·강퇴 v2 이관 — 강퇴 관련 규칙이 그 위에 얹힌다.
- **ADR-0028**: 이벤트 기반 집계 — 랭킹 제외를 `challenge.member.left` 처리에 넣는 근거.
- **ADR-0032**: 챌린지 시작 시 루틴 생성 — `WAITING`에 인스턴스가 없다는 전제의 출처.
- **ADR-0040**: 루틴 인스턴스 독립 — `WAITING`에서만 챌린지 루틴 제목 수정을 허용하는 근거와 같은 전제를 공유한다.
