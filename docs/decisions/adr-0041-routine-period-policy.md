# ADR-0041: 루틴 기간 정책 — 무기한 허용, 과거 시작 제한, 수정 범위

- **Status**: Accepted
- **Date**: 2026-08-23
- **Author**: Routinely Project

---

## 1. Context

`routines`의 기간(`started_at` · `ended_at`)에 대해 세 가지가 정해진 적이 없었다.

1. **종료일이 필수여야 하는가.** 현재 `ended_at DATE NOT NULL`이다. "아침 물 한 잔"처럼 평생 이어갈
   습관에도 종료일을 강제한다.
2. **시작일을 과거로 잡을 수 있는가.** `ended_at >= started_at`만 검증한다. 시작일을 작년으로 넣으면
   작년 전체가 수행 기간이 되어 백필이 무제한으로 열린다. 챌린지는 `@FutureOrPresent`로 막혀 있는데
   개인 루틴만 열려 있다.
3. **기간을 나중에 바꿀 수 있는가.** `PATCH /api/v1/routines/{routineId}`는 선호 시각·요일만 받는다.
   변경 수단 자체가 없고, 기간이 끝나도 자동으로 아무 일도 일어나지 않는다.

ADR-0038의 sparse 저장이 이 셋을 모두 민감하게 만들었다. **미완료 상태를 저장하지 않고 "수행 기간 ∩
조회 구간"을 전개해 파생**하므로, 기간이 곧 판정 범위다. 기간이 바뀌면 과거 판정도 함께 바뀐다.

---

## 2. Decision

### 2.1 개인 루틴의 종료일은 선택이다

| | `ended_at` |
|---|---|
| 개인 루틴 | **NULL 허용** — 비우면 무기한 |
| 챌린지 루틴 | **NOT NULL** — 챌린지 기간과 동일 (애플리케이션 검증) |

종료일을 두는 경우 **기간 상한은 366일**이다. 실행 기록 조회 상한과 같은 값으로 맞춘다.
더 길게 하려면 종료일을 비운다.

### 2.2 개인 루틴 시작일은 90일 전까지 허용한다

챌린지 루틴은 기존대로 오늘 이후만 허용한다(`@FutureOrPresent`).

### 2.3 기간 수정 범위

기준은 **그 수정이 이미 저장된 완료 기록의 해석을 바꾸는가**다.

| 필드 | 완료 0건 | 완료 있음 |
|---|:---:|:---:|
| `started_at` | ✅ | **❌** |
| `ended_at` | ✅ | **⚠️ 연장만** (NULL 전환 포함) |

`ended_at` 단축은 **마지막 완료일 이후로만** 허용한다.

### 2.4 기간이 끝나도 자동 중단하지 않는다

상태 컬럼을 추가하지 않고 **날짜로 파생**한다.

| 파생 상태 | 조건 |
|---|---|
| 진행 중 | `is_active` = true, 오늘 ∈ 기간 (또는 `ended_at` IS NULL) |
| **완료됨** | `is_active` = true, `ended_at` < 오늘 |
| 중단됨 | `is_active` = false |

---

## 3. Rationale

### 3.1 종료일 강제는 개인 루틴의 성격과 맞지 않는다

챌린지는 **유한한 도전**이라 기간이 본질이다("30일 아침 운동"). 반면 개인 루틴은 **습관**이고,
습관에는 끝이 없다. 종료일을 강제하면 사용자는 의미 없는 날짜를 아무렇게나 넣거나, 1년마다 루틴을
다시 시작해야 한다. 후자는 **그때마다 `routine_id`가 갈려 스트릭·달성률이 끊긴다.**

업계 표준 습관 앱(Streaks, Habitica, Loop Habit Tracker)이 공통적으로 종료일을 받지 않는다.
기간이 있는 것은 "챌린지"라는 별도 개념으로 다룬다 — Routinely의 도메인 구분과 정확히 일치한다.

**무기한이 성립하는 이유는 달성률 분모를 "오늘까지 경과한 기간"으로 잡기로 했기 때문이다.**
전체 기간을 분모로 쓰면 종료일이 없을 때 분모를 정할 수 없지만, 오늘까지를 쓰면 시작일만 있으면 된다.
조회에 366일 상한이 있어 파생 비용도 묶인다.

### 3.2 과거 시작을 허용하되 무제한으로 두지 않는 이유는 MISSED 폭탄이다

"이미 3개월 해오던 습관을 등록하고 지난 기록을 채운다"는 정당한 시나리오다. 통계에 "6개월째"가 찍히는
것이 동기부여가 된다.

그러나 무제한이면 작년 1월부터 매일 루틴을 시작했을 때 아직 인증하지 않은 300일이 **한꺼번에 MISSED로
파생**되어 달성률이 0%에 수렴한다. **격려하려고 만든 화면이 정반대로 작동한다.**

90일로 잡은 근거는 습관 형성 주기다. Lally et al.(2010)의 중앙값이 약 66일이므로, 그보다 조금 긴
90일이면 "이미 몸에 붙은 습관"을 등록하기에 충분하다. 분기 단위라 사용자가 이해하기도 쉽다.

**화면 경고가 정책의 일부다.** 과거 날짜를 고르면 즉시 알린다 —
*"2026-06-01부터 시작하면 아직 인증하지 않은 62일이 미완료로 표시됩니다."*

챌린지에 과거 시작을 열지 않는 이유는 랭킹이다. 시작일이 뒤로 밀리면 분모(예정 횟수)와 분자(완료 수)가
모두 흔들려 멤버 간 비교가 무너진다.

### 3.3 시작일은 양방향 모두 위험하고, 종료일은 한쪽만 안전하다

sparse 파생이 "기간 ∩ 조회 구간"을 전개하므로 기간 경계 이동이 곧 판정 범위 이동이다.

| 변경 | 결과 |
|---|---|
| `started_at` 과거로 | 없던 구간이 생겨 **전부 MISSED로 파생** → 달성률 하락 |
| `started_at` 미래로 | 이미 완료한 날이 기간 밖으로 밀려 **기록이 조회에서 사라진다** |
| `ended_at` 연장 | 새 구간은 미래라 PENDING. **안전** |
| `ended_at` 단축 | 완료한 날이 기간 밖으로 밀릴 수 있음 → **마지막 완료일 이후로만** |

`ended_at` 단축의 하한을 "마지막 완료일"로 잡으면 **저장된 완료 행이 하나도 잘리지 않는다.**
이것이 안전의 정확한 조건이다.

### 3.4 "완료됨"을 저장하지 않고 파생하는 것은 sparse 원칙과 같은 결이다

기간이 끝난 루틴에 `COMPLETED` 같은 상태 컬럼을 추가하면, ADR-0038이 실행 기록에서 제거한 것과 같은
문제가 생긴다 — **시스템이 계산할 수 있는 값을 저장하고, 그것을 갱신할 스케줄러가 필요해진다.**
`ended_at < 오늘`은 조회 시점에 결정적으로 계산되므로 저장할 이유가 없다.

**"완료됨"과 "중단됨"을 구분해 표시하는 것이 중요하다.** 끝까지 해낸 루틴을 그만둔 루틴과 같은 회색으로
보여주면, 성취로 남아야 할 것이 실패처럼 읽힌다.

### 3.5 기각한 대안

**종료일 필수 유지 + 상한 366일.** 스키마 변경이 없어 가장 싸다. 그러나 §3.1의 문제(1년마다 재시작 →
기록 단절)가 그대로 남는다. 습관 서비스의 핵심 지표인 스트릭이 1년마다 0이 되는 것은 받아들이기 어렵다.

**과거 시작 전면 금지.** 챌린지와 규칙이 통일되어 단순하다. 그러나 "이미 해오던 습관 등록"을 포기하게 되고,
그 시나리오는 신규 사용자의 첫인상을 좌우한다.

## 4. 스키마

```sql
-- V7__routine_period_policy.sql
ALTER TABLE routines ALTER COLUMN ended_at DROP NOT NULL;

ALTER TABLE routines DROP CONSTRAINT IF EXISTS ck_routines_date_range;
ALTER TABLE routines ADD CONSTRAINT ck_routines_date_range CHECK (
    ended_at IS NULL OR ended_at >= started_at
);

COMMENT ON COLUMN routines.ended_at IS
    '루틴 종료일 — NULL이면 무기한(개인 루틴만). 챌린지 루틴은 애플리케이션에서 NOT NULL을 강제한다';
```

> 챌린지 루틴의 `ended_at` 필수는 **DB CHECK로 걸지 않는다.** `challenge_id IS NULL OR ended_at IS NOT NULL`
> 형태의 제약을 넣을 수는 있으나, 챌린지 여부에 따라 컬럼 필수성이 갈리는 조건부 제약은 스키마를 읽기
> 어렵게 만든다. 인스턴스 생성 경로가 `challenge.started` 소비자 하나로 고정되어 있으므로 그곳에서 보장한다.

### NULL 분기가 필요한 지점

`ended_at`을 nullable로 바꾸면 아래가 모두 "종료일 없음"을 처리해야 한다.

| 지점 | 처리 |
|---|---|
| `RoutineExecutionService.validateWithinPeriod()` | 상한 검사를 건너뛴다 |
| 파생 범위 전개 | `min(ended_at, 조회 종료일)` → `ended_at`이 NULL이면 조회 종료일 |
| 달성률 분모 (#60) | "오늘까지 경과한 기간" 규칙이라 영향 없음 |
| 알림 예약 종료 판정 (PGMQ Next-One, ADR-0017) | 종료일이 없으면 다음 1건을 계속 이어 예약한다 |
| `GET /routines` 응답 | `endedAt: null` 허용 |

## 5. Consequences

### 긍정적
- 개인 루틴이 습관의 성격에 맞게 무기한으로 이어진다. **1년마다 재시작해 스트릭이 끊기는 일이 없다.**
- "이미 해오던 습관 등록"이 가능해지고, MISSED 폭탄은 90일로 묶인다.
- 기간 수정 규칙이 "완료 기록의 해석을 바꾸는가"라는 한 기준으로 정리된다 — ADR-0040의 정의 수정 규칙과 같은 기준이다.
- 기간 종료를 파생으로 처리해 마감 스케줄러가 필요 없다(ADR-0038과 일관).

### 부정적
- **`ended_at` NULL 분기가 여러 곳에 늘어난다**(§4). 빠뜨리면 무기한 루틴에서 파생 범위가 잘못 계산된다.
- 챌린지 루틴의 종료일 필수를 DB가 아닌 애플리케이션이 보장한다.
- 무기한 루틴은 조회 366일 상한이 **유일한 파생 비용 방어선**이 된다. 상한을 푸는 변경을 하면 여기서 터진다.
- 90일이라는 숫자에 강한 근거가 있는 것은 아니다. 사용 데이터를 보고 조정할 여지를 남긴다.

### 구현 영향 (#57)

| 대상 | 변경 |
|---|---|
| V7 마이그레이션 | `ended_at` DROP NOT NULL + CHECK 교체 |
| `RoutineExecutionService.validateWithinPeriod()` | `ended_at` NULL이면 상한 검사 생략 |
| 파생 범위 전개 | `ended_at` NULL 처리 |
| `POST /api/v1/routines` | `endedAt` 선택. `startedAt` 90일 전까지 검증 |
| `PATCH /api/v1/routines/{routineId}` | 기간 수정 수용 + §2.3 규칙 검증 |
| `GET /api/v1/routines` | 진행 중 / 완료됨 / 중단됨 파생 상태 포함 |

## 6. 관련 결정

- **ADR-0038**: sparse 저장 — 기간이 곧 판정 범위가 되는 근거. 기간 종료를 파생으로 두는 것도 같은 원칙.
- **ADR-0040**: 루틴 인스턴스 독립 — 정의 수정 규칙("완료 기록의 해석을 바꾸는가")을 기간에 그대로 적용한다.
- **ADR-0027**: 달성률 캡 — 분모를 "오늘까지 경과한 기간"으로 잡는 결정이 무기한 루틴의 전제다.
- **ADR-0017**: 알림 예약 — 종료일 없는 루틴의 Next-One Chaining 종료 조건에 영향.
